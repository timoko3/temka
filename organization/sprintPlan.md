# Ближайший спринт: 5 независимых задач

> Состояние на входе: `entitySystem` (ECS) написан и покрыт тестами, остальные модули — в черновом виде. Проект **не собирается**: в `makefile` остался git-конфликт, `generalFunctions/` пуст, старая физика ссылается на несуществующий `mathVector.h`.
>
> Цель спринта — получить работающий "движок частиц" + фундамент, на котором можно вести параллельную работу дальше. Спринт рассчитан на **2 недели**, командой из **5 человек**.

---

## Как читать задачи

Каждая задача имеет:
- **Вход** — что должно быть готово до старта.
- **Выход** — что считаем результатом.
- **DoD** — конкретные критерии готовности.
- **Зависимости** — от кого/чего ждём.
- **Контракты** — интерфейсы, которые нужно зафиксировать в первый же день, чтобы не блокировать друг друга.

---

## Горизонтальные контракты (фиксируем в первый день)

1. **Математические типы** (`Vec2`, `Vec3`, `AABB`, `Ray`) — единый API от задачи 2. Все остальные задачи используют их, не заводят свои аналоги.
2. **ECS API** — уже зафиксирован в `entitySystem/documentation.md`. Задачи 3 и 4 используют его без изменений.
3. **Debug-draw API** — минимальный контракт между физикой и рендером: `point(pos, radius, color)`, `line(a, b, color)`, `aabb(box, color)`, `text(x, y, string)`.
4. **Сборочный контракт** — задача 1 определяет, как собирать модули (`make`, `cmake`, пути include), остальные под него подстраиваются.

## Задача 1 — Инфраструктура сборки

**Ответственный:** 1 человек (build / DevOps).

### Вход
- Текущий `makefile` с git-конфликтом.
- ECS тест работает (`make ecs_test`).
- Остальное не собирается.

### Что делать
1. Починить `makefile`: убрать `<<<<<<< HEAD`, убрать дублирование переменных, добавить правила для `core/`, корректную линковку с raylib.
2. Восстановить/заменить `generalFunctions/mathVector.h` либо убрать из include-цепочки, пока не готова задача 2.
3. Добавить цели:
   - `make ecs_test` — запуск ECS тестов.
   - `make physics_engine` — сборка основного бинарника.
   - `make test` — запуск всех тестов.
4. Добавить `.gitignore` для `obj/`, `*.out`, `ecs_test`.
5. (Опционально) начать переход на `CMakeLists.txt`, если команда хочет. Главное — чтобы **один** способ сборки работал стабильно.

### DoD
- `make clean && make && make test` проходит без ошибок.
- `ecs_test` печатает `ALL TESTS PASSED`.
- `physics_engine.out` запускается (пусть пока и без объектов — главное, не падает).

### Зависимости
Нет. Это первая задача, от которой зависят остальные.

## Задача 2 — Математический фундамент

**Ответственный:** 1 человек (math).

### Вход
- codeStyle.
- Понимание, что физика 2D будет использовать `Vec2`, а в будущем — 3D.

### Что делать
1. Создать модуль `math/`:
   - `math/vec2.h`, `math/vec3.h`, `math/vec4.h`
   - `math/mat3.h`, `math/mat4.h`
   - `math/quat.h`
   - `math/aabb.h`
   - `math/ray.h`
   - `math/transform.h`
2. Операции: `+`, `-`, `*`, `dot`, `cross`, `length`, `normalize`, `lerp`, матричное умножение, `inverse`, `transpose`, `lookAt`, `ortho`, `perspective`, кватернионы `fromAxisAngle`/`toMat4`/`slerp`.
3. Покрыть unit-тестами (`math/test.cpp` или в `entitySystem/test.cpp` временно).

### DoD
- Все базовые операции имеют тесты с эталонами.
- `inverse(M) * M ≈ I`, `|normalize(v)| ≈ 1`.
- `Vec2` заменяет `generalFunctions::Vector2d` и `MathVector` в `physicsEngine`.
- `make test` включает математические тесты и они проходят.

### Зависимости
- Задача 1 — чтобы тесты собирались.

### Контракт для других задач
- `Vec2 { float x, y; }`, `Vec3 { float x, y, z; }`.
- `AABB { Vec2 min, max; bool intersects(const AABB&) const; }`.
- `Ray { Vec2 origin, dir; }` (`dir` нормализован).

## Задача 3 — Core: лог, assert, handle, pool, profiler

**Ответственный:** 1 человек (core).

### Вход
- ECS уже есть, но использует собственные примитивы.
- codeStyle.

### Что делать
1. Создать `core/log.h` / `core/log.cpp`:
   - Уровни `Trace`, `Debug`, `Info`, `Warn`, `Error`.
   - Каналы-теги, printf-style API.
   - Макросы `TM_TRACE`, `TM_DEBUG`, `TM_INFO`, `TM_WARN`, `TM_ERROR`.
2. `core/assert.h`:
   - `TM_ASSERT(cond, msg)` и `TM_ASSERT_MSG(cond, fmt, ...)`.
   - В Debug — `abort`, в Release — лог + abort по политике.
3. `core/handle.h`:
   - `Handle32` (index + generation) и `Handle<Tag>`.
4. `core/pool.h`:
   - Поколенческий пул `Pool<T, Tag>`: `create`, `tryGet`, `destroy`, `size`, `forEach`.
5. `core/profiler.h`:
   - `prof::beginFrame`, `prof::scope`, `prof::event`, `prof::dump(path)`.
   - RAII `ProfileScope`.
   - Экспорт в Chrome Trace JSON.

### DoD
- Лог пишется в stdout + опционально в файл; уровни переключаются.
- `Pool` переживает `destroy` + `create` без невалидных хэндлов.
- `prof::dump` открывается в `about:tracing`.
- Core интегрирован хотя бы в ECS для логирования ошибок (по желанию).

### Зависимости
- Задача 1 — чтобы собирать.

### Контракт для других задач
- Лог используется во всех модулях через макросы.
- `ProfileScope` ставится в hot-path физики и рендера.

## Задача 4 — Физика частиц на ECS

**Ответственный:** 1 человек (physics).

### Вход
- ECS готов.
- Математические типы от задачи 2.
- Core от задачи 3 (для логов/профайлера).

### Что делать
1. Переписать `physicsEngine/objects.h` на ECS:
   - Компоненты: `Position`, `Velocity`, `Mass`, `Force`, `ParticleTag`.
   - `ParticleWorld` — мир частиц.
2. Интеграторы:
   - Explicit Euler.
   - Semi-implicit Euler.
3. Силы:
   - Гравитация.
   - Drag (linear).
4. Границы мира:
   - AABB-граница, отскок с restitution.
5. Fixed timestep с аккумулятором (можно переиспользовать `core/simulation.cpp`).
6. Golden replay:
   - Запись позиций частиц в файл.
   - Повторный прогон сравнивается с эталоном побайтово.

### DoD
- Симуляция частиц запускается headless и воспроизводится (golden replay).
- Аналитические тесты: свободное падение, равномерное движение.
- 1000 частиц стабильно работают за <16 мс/шаг.
- `physicsEngine` собирается и проходит тесты.

### Зависимости
- Задача 1 (сборка).
- Задача 2 (математика).
- Задача 3 (лог/профайлер) — soft-зависимость, можно обойтись `printf` временно.

### Контракт для рендера
- `ParticleWorld` предоставляет список позиций и радиусов для отрисовки.
- Или рендер получает данные через `DebugDrawComponent`.

## Задача 5 — Графический тестовый стенд

**Ответственный:** 1 человек (render).

### Вход
- ECS готов.
- Математические типы от задачи 2.
- Raylib уже используется в `graphicsEngine/render.cpp`.

### Что делать
1. Создать модуль `graphicsEngine/`:
   - `Renderer` — обёртка над окном raylib.
   - `Camera2D` — pan/zoom, ортографическая проекция.
   - `DebugDraw` — интерфейс отрисовки примитивов.
2. Примитивы:
   - `point(pos, radius, color)`
   - `line(a, b, color)`
   - `aabb(box, color)`
   - `circle(center, radius, color)`
   - `text(x, y, string, color)`
3. Интерактив:
   - WASD — перемещение камеры.
   - Колёсико мыши — zoom.
   - FPS и счётчик объектов на экране.
4. Визуализация:
   - Сетка мировых координат.
   - Отрисовка частиц из задачи 4 (через массив позиций).

### DoD
- Приложение `playground` запускается, показывает сетку и частицы.
- Камера управляется мышью/клавиатурой.
- FPS и число объектов отображаются корректно.
- Рендер не зависит от внутренностей физики — только от публичных данных.

### Зависимости
- Задача 1 (сборка).
- Задача 2 (математика).
- Задача 4 (физика частиц) — soft-зависимость; можно тестировать на фейковых точках, пока физика не готова.

## Риски и что делать

| Риск | Митигация |
|------|-----------|
| Задача 1 затягивается | Пока она идёт, остальные пишут код в изолированных `test.cpp` / `main.cpp` с `-I.`. |
| Несовпадение математических типов | Зафиксировать `Vec2`/`Vec3` в первый день и не менять до конца спринта. |
| Рендер ждёт физику | Рендер сначала рисует фейковые точки, интеграция в день 8. |
| ECS не подходит для физики | Тестировать на 1000 сущностях в день 8; если тормозит — упрощаем до bare-массивов, но уже с известным API. |
